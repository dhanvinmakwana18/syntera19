# Syntera Engineering Rules

This document outlines the strict engineering principles governing the Syntera codebase. 

## 1. HARD RULES
These rules **must not** be broken without explicit architectural consensus and justification.

1. **Do not duplicate execution engines.** 
   - `ExecutionGraph` is the definitive generic execution foundation. All multi-step, agentic, or chained workflows MUST be built on top of this DAG.
2. **Do not bypass existing abstractions.**
   - Do not directly instantiate vendor-specific SDKs (e.g., `openai.Client`) inside application logic. Always use `backend/providers/llm.py` or the upcoming `ModelRouter`.
3. **Do not silently break existing functionality.**
   - All architectural additions must preserve backward compatibility where practical.
4. **Tests must accompany meaningful changes.**
   - Code changes that alter logic, add features, or fix bugs must include corresponding unit/integration tests.
5. **Benchmark claims must come from actual measurements.**
   - Do not claim a model, chunker, or hardware configuration performs at a certain speed or accuracy without empirical, reproducible data attached to the PR/ADR.
6. **Do not claim capabilities that have not been demonstrated.**
   - Aspirational features must be clearly marked as "Planned" or "Experimental" in documentation.
7. **Model providers must remain replaceable.**
   - The architecture must never hardcode a dependency on a single model family (e.g., GPT-4 or Llama).
8. **Never allow unrestricted self-modification.**
   - The Evolution Engine (when fully implemented) must be controlled by measurable evaluation criteria. AI-generated changes must be evaluated in a sandbox/test-suite before promotion.
9. **Local and remote inference must remain provider-abstracted.**
   - Application logic should not know whether a response was generated by an RTX 4050 or an external API. `ModelRouter` owns this complexity.

## 2. ENGINEERING RECOMMENDATIONS
These are strong guidelines that should be followed unless a specific edge-case requires deviation.

1. **Prefer modular components.**
   - Design classes to do one thing well (e.g., `MemoryRetriever` bridging `MemoryStore` into the RAG pipeline).
2. **Use explicit interfaces/contracts.**
   - Define data shapes using Pydantic models in `contracts.py` files for each domain before writing implementation logic.
3. **Avoid unnecessary framework dependencies.**
   - Prefer standard library or lightweight libraries over massive monolithic frameworks (e.g., avoid LangChain if a 50-line Python class achieves the same result faster and with more transparency).
4. **Prefer simple solutions over unnecessary complexity.**
   - Do not over-engineer features before they are strictly needed. 
5. **Model selection belongs in ModelRouter.**
   - Do not leak model routing logic (cost checks, token counting for fallback) into API routers or core nodes.
